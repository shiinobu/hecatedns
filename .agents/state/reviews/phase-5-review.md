# Phase 5 review (cheap, narrow scope)

Reviewer: `xdns-reviewer` run on Sonnet (fresh context, read-only, Master's quota rule: spare Opus), 2026-10-19. Range `4c7220e..28e0769` (Go only) plus the then-untracked `scripts/autostart.ps1`. The reviewer did not run the whole-repo gates; the main session ran them (see the end). Report text saved by the main session; the status table at the end tracks the fixes.

The reviewer made 3 experiments in a scratch copy of the repository (the repo itself was not touched).

## Verdict

0 Critical, 1 Important, 5 Minor. Nothing in the range blocks Phase 6. The Important item sat on the exact scenario `autostart.ps1` describes.

## Important

**I1 - the fatal "why did xdns stop" error never reaches `xdns.log` - `cmd/xdns/run.go:68-71` (with `79-81`, `122`).** `serve` returns the startup or run error after `defer closeRunLog()` has run; `runServerCtx` then prints `xdns run: <err>` to the raw `stderr`, not to the tee. No backend logs its start failure either. Scenario: at boot Wi-Fi has not yet given 192.168.1.99, `net.ListenPacket` fails and xdns exits; under Task Scheduler (S4U, hidden, no console) the message goes nowhere, `xdns.log` has no line, `status` shows only `LastTaskResult 0x1`, and the retry loop repeats it every minute with no trace. Fix direction: log the returned error through the logger before the deferred close (a config-load failure cannot be persisted because the log dir comes from the config; document "run `xdns check` after editing the config").

## Minor

**M1 - `runlog` rotation failure handling, both cases reproduced - `internal/runlog/runlog.go:93-102`, `76-90`.** (a) If `Close` and `Rename` succeed but `openCurrent` fails (disk full at that moment, antivirus), `f.file` stays the old closed handle and every later `Write` returns "file already closed" until the process restarts. (b) On Windows `os.Rename` fails with a sharing violation while someone has `xdns.log` open (for example `Get-Content xdns.log -Wait`, the obvious way to watch it): at the cap every `Write` returned `n=0` plus the rename error and the lines were lost (console only, which a task does not have); it recovered once the reader closed. Fix direction: keep appending to the current file on a rotate error, or set `f.file = nil` and reopen lazily; count the failure; tests for both paths.

**M2 - `qlog` `pending` is not reset when `bufio` flushes by itself - `internal/qlog/writer.go:299`, `307-316`, `384`.** `bufio.Writer.Write` flushes automatically whenever the 64 KB buffer fills; those records are on disk but stay in `pending`. Reproduced: 400 records, then the disk fills, then `flush()`: `written=0 dropped=400 linesOnDisk=333`. No record is lost uncounted, duplicated or merged; the counters over-state drops, and only under load (more than about 330 queued records without the queue going idle) after a failure. `dayBytes` also counts bytes that were discarded. Fix direction: after `out.Write`, if `out.Buffered()` shrank an auto-flush succeeded, so `pending = 1`.

**M3 - upstream-health warning: flapping floods, and busy/SERVFAIL edge cases - `internal/engine/health.go:58-70`, `internal/backend/native/handler.go:159-162`, `internal/backend/native/upstream.go:124-126`.** (a) `answered()` resets `lastWarn` once a warning was due; under a flapping link (5 failures, 1 success, repeated) it alternates WARN "keep failing" and INFO "answer again" with no throttle. (b) `errBusy` ("too many upstream queries in flight") goes through `Failed`, so one noisy client that fills its slots can produce "upstream servers keep failing" although it is a local limit. (c) The pool returns an upstream's SERVFAIL/REFUSED as a normal answer, so `After` carries `Upstream` and resets the counter; an upstream that SERVFAILs everything never warns (a design choice, the message promises "clients get SERVFAIL"). Fix direction: keep the one-minute throttle across recoveries and send the "back" message only if a warning was emitted; do not count `errBusy`; (c) optional.

**M4 - lost-update window between `failed` and `answered` - `internal/engine/health.go:39-54` against `62-69`.** A `failed` call that reached n=5 can be overtaken by `answered` (Swap(0) plus `lastWarn` reset), so a stale "keep failing" warning can appear after "answer again" with the counter at 0. Cosmetic, at most one stale line per race; fold both into one mutex-guarded struct if M3 is reworked.

**M5 - `scripts/autostart.ps1` small points.** A relative `-Root` is joined as-is, so the task would be registered with a relative `Execute` and `WorkingDirectory` and fail at boot (use `Resolve-Path`). `Stop-ScheduledTask` in `remove` (and a Windows shutdown) ends xdns with TerminateProcess, so nothing is flushed gracefully (the query log survives because it flushes whenever the queue is idle). The retry window is 365 days from each boot (documented). `-Hidden` makes the task invisible in the Task Scheduler UI by default; `status` and `remove` work by name. None is a logic error in the install, remove or run-twice flow.

## Verified correct (by the reviewer)

- `health.go` and its call sites: cache hits (`Meta{Cached:true}`), local reverse and ANY (`Meta{}`) and the dnsproxy `ErrNoUpstreams` path all have an empty `Meta.Upstream`, so they neither clear nor trigger the counter; dnsproxy cache hits have `dctx.Upstream == nil`; `context.Canceled` is ignored and the wrapping chains (`plainUpstream` `%w`, pool `errors.Join`, DoH `url.Error`) keep `errors.Is` true; `DeadlineExceeded` counts; `failures` is atomic, `lastWarn` is under a mutex; `log` is never nil.
- `qlog/writer.go`: `Reset` after a failed write or flush unblocks bufio's sticky error; `written.Add(^(pending-1))` correctly subtracts `pending`; `fail` is called once per failed record and the flush path uses `reportFailure` only (no double count); the `torn` flag puts the next record on a fresh line and the reader skips blank and damaged lines; the flag resets on rotation; `shutdown` still drains, flushes and closes; all writer state is owned by the writing goroutine and the counters are atomic.
- `runlog`: `0o700`/`0o600`; a single oversize write is kept whole; the size is counted from the existing file; concurrent writers are serialized; `Close` is idempotent and a write after `Close` returns `ErrClosed`; `Tee` writes the file first and always returns the console's result, so a log failure can never stop the server or hide the console line; in `run.go`, `closeRunLog` is deferred first and runs last, after the query log's "closed" line; the names `xdns.log` and `xdns.log.1` do not match the `queries-YYYYMMDD.jsonl` retention sweep; renaming over a closed file works on Windows.
- Native review-fix commits: `bootstrap.shareOfDeadline` (the last part gets everything left, no deadline pass-through, no leaked or wrongly shadowed `cancel`; the dial gets its own budget because net/http detaches the dial context); `plainUpstream.send` (LIFO order `stop()` then `conn.Close()`, `AfterFunc` stopped on every return path including the TCP retry, a double close is harmless, `ExchangeWithConnContext` of miekg v1.1.73 applies the context deadline like `ExchangeContext`); RA (`got.RecursionAvailable=true` mutates a `Copy()` from the cache, never the stored message); `localreverse` (`ExtractReversedAddr` lower-cases and trims the dot, so case-randomized PTR names are covered; only PTR, SOA and NS, as in dnsproxy; a fresh message with a synthetic SOA, answered before the cache and the gate); the `server.go` split (pending accounting preserved, `errors.Join` returns nil when nothing failed, sockets closed after the `Shutdown` calls); the new conformance cases assert both the answer and that nothing reached the upstream.
- Project rules: functions and files within limits (largest non-test file in range `writer.go`, 414 lines); each feature and fix commit ships its tests; `health_test.go` covers threshold, throttle, recovery, cache, local, cancel, nil error and concurrency.
- `autostart.ps1`: the path with spaces is quoted correctly in `-Argument` (`-Execute` and `-WorkingDirectory` rightly unquoted); install checks admin, the exe, the config (`xdns check`) and an existing task before changing anything; a second `install` throws "already exists" with no partial state and `remove` twice is a no-op message; `remove` is stop then unregister, the full rollback of this script (the firewall rule is outside it); defaults are sound (limited run level, S4U with no stored password, no battery or network conditions, `IgnoreNew`, no time limit).

## Not verified by the reviewer

- The script was not run (it needs an elevated session and changes Windows); the Task Scheduler behaviour (AtStartup trigger with repetition, S4U, `Stop-ScheduledTask` ending the process) was read, not executed. Master's by-hand test is the evidence (see `docs/phase-5-report.md`).
- `dnsproxybe` shutdown: not confirmed that dnsproxy's `Resolve` wraps `context.Canceled` with `%w`. If it does not, a shutdown with 5 or more in-flight queries could print one spurious "keep failing" line on that backend only.
- Real full-disk behaviour of `os.File` on NTFS (partial writes); only the fake disk in the tests was seen.
- Whole-repo gates and the race detector (the main session's job).
